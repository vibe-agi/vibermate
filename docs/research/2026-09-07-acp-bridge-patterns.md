# ACP bridge implementation patterns

Date: 2026-09-07. Scope: a Go ViberMate wrapper between an existing ACP client and an existing ACP agent, not another coding agent. This is source research and a staged recommendation, not a claim of shipped ACP capture support.

Sources were discovered through the ACP project's agent/library listings, then checked against live GitHub metadata, pinned source, tests, and CI. Third-party source was cloned for reading only. No adapter, third-party test suite, installer, or live model API was executed; no account credentials were read. The survey is deliberately deeper on the implementations relevant to this boundary, not a claim to have audited every ACP project.

## Recommendation

Use the existing active Claude/Codex adapters as child programs. Keep ViberMate's first ACP layer byte-opaque and bounded, behind its existing process-supervision seam. Add per-session metadata observation separately; design the server/UI evidence model only after that boundary is explicit. Do not turn the current HTTP launcher into an ACP agent implementation or claim that successfully forwarding stdio automatically enables HTTP routing, content retention controls, or per-workspace authorization.

The active Codex adapter already starts Codex App Server and translates its events into ACP. The Claude adapter uses the official Claude Agent SDK. Their respective translation, tool, permission, history, and subagent machinery should remain upstream responsibilities. Both depend on the official TypeScript ACP SDK. Sources: [Codex process adapter](https://github.com/agentclientprotocol/codex-acp/blob/1a3c01e8ca317f83e3b60bc5632cf052882bea15/src/CodexJsonRpcConnection.ts#L15-L42), [Codex dependencies](https://github.com/agentclientprotocol/codex-acp/blob/1a3c01e8ca317f83e3b60bc5632cf052882bea15/package.json), [Claude dependencies](https://github.com/agentclientprotocol/claude-agent-acp/blob/3e23c5b960b66a6d2c892e7524c952e731c076a7/package.json#L67-L70).

## Transport: forward first, observe separately

ACP stdio consists of newline-delimited UTF-8 JSON-RPC messages. The client launches the agent; stdout is exclusively protocol traffic and stderr is separate diagnostic output. Agent-to-client requests are normal: permission, filesystem, and terminal calls can occur while a client prompt request remains outstanding. A sequential request/response loop deadlocks this relationship. Sources: [transport rules](https://github.com/agentclientprotocol/agent-client-protocol/blob/0d6f1549583064f898661179d41aba5044c49b3e/docs/protocol/v1/transports.mdx), [bidirectional cancellation example](https://github.com/agentclientprotocol/agent-client-protocol/blob/0d6f1549583064f898661179d41aba5044c49b3e/docs/protocol/v1/cancellation.mdx#L40-L68).

Recommended invariants:

- Two independently progressing byte paths plus independently drained stderr; no human prompt, banner, progress text, color conversion, or diagnostic JSON on protocol stdout.
- No JSON decode/re-encode on the forwarding path. Preserve IDs exactly, both directions, including simultaneous same-valued IDs belonging to different initiators. Do not generate requests or rewrite capabilities in the transport foundation.
- Unknown fields, methods, `_meta`, notifications, and future union variants pass unchanged. Parse failures in a later observer do not justify dropping/rewriting a message that the actual peers may understand.
- Bound transport buffers independently of message size. Backpressure the corresponding input when its output blocks; do not accumulate unbounded messages or allow a slow observer/database to stall both directions.
- A later observer may have a bounded maximum *observed* frame size and report observation unavailable for larger frames. That is not a license to truncate forwarded bytes, silently mark capture complete, or log the oversized contents.

These are ViberMate design recommendations derived from the wire boundary. `_meta` is explicitly extensible, and root fields are reserved for future versions: [extensibility](https://github.com/agentclientprotocol/agent-client-protocol/blob/0d6f1549583064f898661179d41aba5044c49b3e/docs/protocol/v1/extensibility.mdx#L8-L48). The official Rust SDK separately identifies stable v1 and draft v2 APIs: [version boundary](https://github.com/agentclientprotocol/rust-sdk/blob/726c5030bfaa88cfdac2fb1f71a63abb331ce586/README.md#L53-L62). A transparent relay need not prematurely translate between them.

### SDK reuse without losing transparency

The Go SDK supplies generated protocol types, concurrent JSON-RPC request handling, ordered notifications, cancellation, and useful synthetic tests. It has no Go module dependencies at the inspected revision. However, its connection parses messages and serializes new envelopes, has a 10 MiB Scanner ceiling, and logs raw malformed input in its default diagnostic path. Generated structs do not preserve arbitrary future root fields. Therefore do not put `NewAgentSideConnection` plus `NewClientSideConnection` in the middle and describe that as byte-transparent. Sources: [connection read path](https://github.com/coder/acp-go-sdk/blob/0845a3bb9eddda5bfc22a94dd3598c90cb842451/connection.go#L366-L459), [write path](https://github.com/coder/acp-go-sdk/blob/0845a3bb9eddda5bfc22a94dd3598c90cb842451/connection.go#L609-L620), [generated session type](https://github.com/coder/acp-go-sdk/blob/0845a3bb9eddda5bfc22a94dd3598c90cb842451/types_gen.go#L3236-L3262), [go.mod](https://github.com/coder/acp-go-sdk/blob/0845a3bb9eddda5bfc22a94dd3598c90cb842451/go.mod).

Reuse selected SDK types only for a separate, explicitly versioned metadata decoder or test client, retaining the original bytes as the forwarding authority. Disable payload-bearing SDK diagnostic output in production. Do not import a full SDK merely to avoid a small opaque `io.Reader`/`io.Writer` transport seam.

The official Rust conductor is a real existing semantic-proxy implementation, not just a proposal. It uses provisional `_proxy/initialize` and `_proxy/successor` envelopes and optionally adapts MCP-over-ACP; that is a larger product choice than supervising one child. Consult [current protocol](https://github.com/agentclientprotocol/rust-sdk/blob/726c5030bfaa88cfdac2fb1f71a63abb331ce586/md/protocol.md), not [the explicitly historical proxy design](https://github.com/agentclientprotocol/rust-sdk/blob/726c5030bfaa88cfdac2fb1f71a63abb331ce586/md/proxying-acp.md#L1-L12). Recommendation: borrow its invariants/tests now; evaluate embedding it only if ViberMate intentionally becomes a protocol-transforming proxy/conductor.

## Process ownership, EOF, and cancellation

The best source reference is the official Rust SDK's `AcpAgent`, which starts a dedicated Unix process group, guards descendants including `npx → node` launchers, races process exit against protocol completion, and bounds shutdown drains. It also keeps stdout progressing while draining stdin. Sources: [process group and guard](https://github.com/agentclientprotocol/rust-sdk/blob/726c5030bfaa88cfdac2fb1f71a63abb331ce586/src/agent-client-protocol/src/acp_agent.rs#L245-L335), [duplex EOF and bounded shutdown](https://github.com/agentclientprotocol/rust-sdk/blob/726c5030bfaa88cfdac2fb1f71a63abb331ce586/src/agent-client-protocol/src/acp_agent.rs#L680-L778).

Recommended Go ownership contract:

1. One supervisor owns spawn, process-group signals, exit status, and final reap. Transport owns its child pipe endpoints, not the process or caller-owned terminal/stdin handles.
2. GUI stdin EOF half-closes the child's stdin; continue draining its final stdout/stderr. Then apply a bounded grace period and group termination if it will not exit.
3. Child exit must not wait forever for the GUI's still-open stdin. Cancel only the wrapper's input pump using an owned cancellable/readiness mechanism; avoid leaking a blocked reader goroutine or closing caller-owned input.
4. A child that closes stdout but stops reading stdin cannot indefinitely hold a final write. Pending undelivered output must yield a failure, not a fabricated successful session.
5. Preserve real child failure/signal status. Escalation must cover still-running descendants even if a wrapper child exits first; a process group is lifecycle containment, not a sandbox against deliberately escaping processes.
6. Forward `session/cancel` and `$/cancel_request` as protocol traffic, not as process termination. They can be session/request scoped while sibling sessions remain active. Cancellation is complete when the peer's corresponding response arrives, not when the notification was written.

ViberMate already has relevant native building blocks: [process-group setup, foreground terminal handling, and signal forwarding](../../internal/runlauncher/process_unix.go), [single child supervision](../../internal/runlauncher/launcher.go). It should deepen these seams rather than maintain two unrelated supervisors. Existing HTTP launch recipes still modify selected client arguments and freeze process `cwd`; neither constitutes an ACP per-session contract: [current launch recipe](../../internal/runlauncher/invocation.go), [remote workspace attestation](../../internal/runlauncher/remote.go).

ACP permits final updates after `session/cancel` and requires the prompt's completion response; pending permissions are resolved by the actual client. A wrapper must not synthesize permission approval or terminate the stream early. [Prompt cancellation requirements](https://github.com/agentclientprotocol/agent-client-protocol/blob/0d6f1549583064f898661179d41aba5044c49b3e/docs/protocol/v1/prompt-turn.mdx#L312-L345).

The smaller `acp-core` recorder is not a substitute for these lifecycle guarantees. Its source unconditionally joins the client-input reader even after noting it may still be blocked; it also waits on the direct child without a bounded process-group guard. These are source-review concerns, not locally reproduced failures. [Proxy teardown](https://github.com/ky2renzzz/acp-core/blob/173cc7cadb6659354ccaafcfe6b08d3c94aee096/crates/acp-proxy/src/lib.rs#L184-L204).

## Terminal authentication is a different invocation

Terminal authentication stabilized on August 20. A supporting client starts a separate interactive process using the same configured agent invocation, appends the advertised `args`, overlays advertised `env`, waits for exit status zero, then reconnects and initializes ACP again. This is not an `authenticate` request, and the standard descriptor cannot supply another executable. [Current authentication contract](https://github.com/agentclientprotocol/agent-client-protocol/blob/0d6f1549583064f898661179d41aba5044c49b3e/docs/protocol/v1/authentication.mdx#L169-L188), [stabilization history](https://github.com/agentclientprotocol/agent-client-protocol/blob/0d6f1549583064f898661179d41aba5044c49b3e/docs/rfds/auth-methods.mdx#L184-L190).

For an illustrative future configuration `vibermate acp -- claude-agent-acp`, the client can consequently invoke `vibermate acp -- claude-agent-acp --cli auth login --claudeai`. Those appended flags belong to the child. The wrapper must neither consume them nor demand NDJSON on the separate login terminal. It must give the child real interactive stdio/TTY, preserve environment/argument order and exit status, and never record login output as ACP evidence. This needs an explicit/testable invocation-mode contract, not credential discovery by inspecting stdout.

Claude advertises exactly these terminal login arguments and routes `--cli` to its native CLI using inherited stdio, before processing its own version flag. [Advertised methods](https://github.com/agentclientprotocol/claude-agent-acp/blob/3e23c5b960b66a6d2c892e7524c952e731c076a7/src/acp-agent.ts#L1964-L2017), [CLI dispatch and signals](https://github.com/agentclientprotocol/claude-agent-acp/blob/3e23c5b960b66a6d2c892e7524c952e731c076a7/src/index.ts#L9-L44). Its legacy `_meta["terminal-auth"]` extension can name a command directly; that older route may bypass the wrapper and needs separate client-specific acceptance, not silent rewriting. [Legacy descriptor](https://github.com/agentclientprotocol/claude-agent-acp/blob/3e23c5b960b66a6d2c892e7524c952e731c076a7/src/acp-agent.ts#L2019-L2033).

Keep ViberMate Runtime User login distinct from the agent's provider login. Reuse ViberMate's existing authenticated local/remote runtime access for management; ACP `authenticate` and gateway/provider credentials continue to belong to the agent/client relationship. No temporary human account per ACP session, no prompting for a ViberMate password on protocol stdin, and no automatic translation of provider logout into Runtime User logout. The Codex adapter's gateway method is an explicitly negotiated extension, not a generic ACP token scheme. [Codex auth negotiation](https://github.com/agentclientprotocol/codex-acp/blob/1a3c01e8ca317f83e3b60bc5632cf052882bea15/src/CodexAuthMethod.ts#L48-L83).

## Session identity, workspace, and duplicate evidence

One ACP process is not one session and not one workspace. `session/new` carries `cwd` and returns an opaque session ID; `session/load` replays history before its response; `session/resume` reconnects without replay; supported forks produce a distinct session. Keep capability negotiation intact rather than inventing unsupported resume/fork behavior. [Session lifecycle](https://github.com/agentclientprotocol/agent-client-protocol/blob/0d6f1549583064f898661179d41aba5044c49b3e/docs/protocol/v1/session-setup.mdx), [Codex per-session map and setup](https://github.com/agentclientprotocol/codex-acp/blob/1a3c01e8ca317f83e3b60bc5632cf052882bea15/src/CodexAcpServer.ts#L606-L704), [Codex load/resume/fork](https://github.com/agentclientprotocol/codex-acp/blob/1a3c01e8ca317f83e3b60bc5632cf052882bea15/src/CodexAcpServer.ts#L777-L835), [Claude load replay](https://github.com/agentclientprotocol/claude-agent-acp/blob/3e23c5b960b66a6d2c892e7524c952e731c076a7/src/acp-agent.ts#L2139-L2167).

A separate metadata observer should correlate setup requests and successful responses by connection generation, initiating direction, and opaque request ID. The eventual server model also needs Runtime User/machine/agent provenance and the native session ID; scope alone is not permission. Process launch `cwd` is a launch fact; a later session's `cwd`/additional roots are distinct, untrusted workspace claims needing validation and provenance. Do not overwrite a frozen Capture workspace or reuse its authority merely because a new ACP session appeared.

Persisting session metadata must not imply retaining prompts, transcripts, tool arguments, MCP secrets, or authentication `_meta`. The child agent remains the owner of native session restoration. A ViberMate database row cannot make an agent without load/resume support resumable. This is consistent with ViberMate's existing [Client Session/Capture separation](../adr/0002-client-sessions-cross-capture-boundaries.md), but ACP-specific claims need their own design before implementation.

Treat load replay as historical presentation, not new model usage. ACP `session/prompt` is a human/agent interaction boundary; it may contain multiple provider exchanges and tool calls, and the HTTP layer may also observe title generation or internal requests. Do not fabricate a one-to-one mapping, double-count ACP updates plus HTTP turns, or deduplicate by matching text/time. The adapter itself already separates history replay and active prompts, and Codex keeps title generation as a separate component. [History path](https://github.com/agentclientprotocol/codex-acp/blob/1a3c01e8ca317f83e3b60bc5632cf052882bea15/src/CodexAcpServer.ts#L777-L801), [title generator](https://github.com/agentclientprotocol/codex-acp/blob/1a3c01e8ca317f83e3b60bc5632cf052882bea15/src/TitleGenerator.ts).

## Retention must be explicit, including side channels

The transport foundation should retain no ACP payloads. Later recording must obey an explicit server-owned policy independently of forwarding; disabling content retention must avoid serializing/enqueuing full payloads for later disposal, not merely hide a UI panel. Keep bounded counters/status and label incomplete observation honestly.

Do not enable upstream debugging as an accidental recorder. Codex's optional `APP_SERVER_LOGS` logger writes App Server input/output verbatim and startup configuration; Claude's optional `CLAUDE_AGENT_LOGS` creates a log file. Stderr can also contain secrets/content and is not inherently safe to retain. This does not mean ViberMate can promise the child agent itself never writes history. Sources: [Codex raw stream logging](https://github.com/agentclientprotocol/codex-acp/blob/1a3c01e8ca317f83e3b60bc5632cf052882bea15/src/CodexJsonRpcConnection.ts#L45-L60), [Codex optional log sink](https://github.com/agentclientprotocol/codex-acp/blob/1a3c01e8ca317f83e3b60bc5632cf052882bea15/src/Logger.ts#L8-L45), [Claude logging and disposal](https://github.com/agentclientprotocol/claude-agent-acp/blob/3e23c5b960b66a6d2c892e7524c952e731c076a7/src/index.ts#L55-L103).

## Acceptance tests to borrow, not another implementation to port

Use synthetic children/clients and bounded test deadlines first. The official Rust SDK provides especially relevant regression cases:

- EOF must flush accepted final responses while keeping duplex reads alive: [transport-close tests](https://github.com/agentclientprotocol/rust-sdk/blob/726c5030bfaa88cfdac2fb1f71a63abb331ce586/src/agent-client-protocol/tests/jsonrpc_transport_close.rs#L281-L626).
- Huge stderr without a newline, delayed nonzero exit, stdout EOF without process exit, blocked outgoing drain, wrapper grandchildren: [process tests](https://github.com/agentclientprotocol/rust-sdk/blob/726c5030bfaa88cfdac2fb1f71a63abb331ce586/src/agent-client-protocol/src/acp_agent.rs#L1037-L1351).
- Request-scoped cancellation must stay responsive while other work runs: [Go cancellation tests](https://github.com/coder/acp-go-sdk/blob/0845a3bb9eddda5bfc22a94dd3598c90cb842451/connection_cancel_test.go), [Rust cancellation tests](https://github.com/agentclientprotocol/rust-sdk/blob/726c5030bfaa88cfdac2fb1f71a63abb331ce586/src/agent-client-protocol/tests/jsonrpc_request_cancellation.rs).
- Load replay must finish before the matching response is considered complete, but unrelated future notifications must not hold completion: [Go notification barriers](https://github.com/coder/acp-go-sdk/blob/0845a3bb9eddda5bfc22a94dd3598c90cb842451/connection_notification_barrier_test.go), [Rust session ordering](https://github.com/agentclientprotocol/rust-sdk/blob/726c5030bfaa88cfdac2fb1f71a63abb331ce586/src/agent-client-protocol/tests/session_ordering.rs).
- Compare opaque input/output bytes, not normalized JSON; add unknown extensions, split UTF-8, CRLF, multi-megabyte image frames, short writes, and same-valued IDs in opposite directions. The small recorder's [byte-exact test](https://github.com/ky2renzzz/acp-core/blob/173cc7cadb6659354ccaafcfe6b08d3c94aee096/crates/acp-cli/tests/e2e.rs#L95) is a useful starting idea, not sufficient acceptance.
- Real terminal-auth acceptance must verify inherited TTY, child-owned appended flags, descriptor env precedence, nonzero/signal exit, reconnect, and absence of captured credentials. Test both standard and legacy client flows separately.

## Staged delivery boundary

1. **Opaque transport foundation:** byte-exact duplex streams, bounded memory, clear pipe ownership, integration with the established process supervisor, no content retention or claimed per-session authorization. Terminal-auth passthrough has its own invocation tests.
2. **Session metadata observation:** an isolated decoder with bounded budgets and no payload-bearing logs; distinguish setup/new/load/resume/fork, replay, cancellation, and disconnected generations. Preserve unknown traffic even when semantic observation is unsupported.
3. **Server/UI integration:** explicitly model ACP session workspace claims, Runtime User ownership, frozen traffic/evidence policy, optional content recording, HTTP-to-ACP correlations, and truthful unavailable/incomplete states. Review this model before reusing old experimental ACP capture fields.
4. **Compatibility acceptance:** pinned active Claude/Codex adapters and actual target GUI clients; native adapter login and multi-workspace scenarios; synthetic protocol tests first, opt-in credentialed tests later. Passing transport tests alone is not a claim that all agents' HTTP routing or all GUI clients are supported.

This approach reuses the difficult agent adaptations and battle-tested lifecycle patterns while keeping ViberMate's distinct responsibilities—runtime identity, traffic policy, and evidence retention—owned by ViberMate.
