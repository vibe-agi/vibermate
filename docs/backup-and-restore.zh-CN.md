# 备份与恢复

ViberMate 的备份是一个新的本地目录，附带经过校验的清单。它不是正在使用的
`runtime.db` 的直接拷贝，不会上传到云端，也不会导出凭据。

## 包含哪些内容

- 必需的控制库、布局中声明且仍存在的观察库和旧历史归档，以及各库保留的 WAL 文件；
- 保存在数据目录中的 Runtime 配置；
- 本机 Proxy CA，包括它的私钥；
- `backup-manifest.json`，记录 Runtime schema 标识，以及每个文件的 SHA-256、大小和
  相对路径。分离布局使用 `vibermate-data-backup/v2`，绑定布局文档和 ID，以及各角色的
  路径、标识、版本、必需标记、状态和归档 ID；仍支持严格读取旧 v1 格式。
- `storage-layout.json`、录制初始化证明、隐私拒绝元数据和维护证书。

创建、验证、移动或恢复前，先停止 Runtime 和附着的 Server 宿主。验证在独立拥有的数据库/
WAL 副本上进行，不改变来源数据库字节。只排除声明角色路径下的 SQLite SHM，保留各角色
的 WAL；其他持久化文件继续遵守原有复制规则。

`verified` 表示角色的精确 schema、完整性和外键检查通过；控制库还检查必需状态不变量，
当前观察库还验证完整隐私拒绝链和已知内部存储编码。已存在的旧归档标记为 `unverified`：
其 schema、文件清单和原始/维护后来源证明已验证，但未穷尽重新解释旧可选载荷语义；
字节完整保留。缺失的可选角色明确标记为 `absent`。后两种状态都令 `historyComplete=false`。
即使为 true，也只表示全部声明角色满足本备份契约，不能保证尽力录制曾捕获全部活动。

必需控制库缺失、清理意图/claim/receipt 未完成、残留保留名称的清理文件、必需隐私拒绝
证明丢失、当前内部编码损坏或归档来源证明不匹配时，拒绝完成。无必需隐私证明依赖的
可选历史可以明确作为缺失保留；恢复保留初始化证明，不会悄悄创建空白历史。必需控制
仍可独立打开。清理保留的无载荷拒绝标识与未知所有权元数据继续包含在副本中；已完成
维护证书中的 `countsExact=false` 表示无法精确统计移除数量，不等于尚未完成，也不宣称
精确的物理字节擦除。

数据库和 Proxy CA 属于敏感数据，备份格式不会对它们加密。Runtime 目录中的服务器访问/
恢复配置也会一并保留。请像保护原始 Runtime 数据目录一样保护备份目录。
清单用于发现意外改动并检查内部一致性；它不是数字签名，如果攻击者能同时替换文件和
清单，它无法证明备份的来源。

## 不包含哪些内容

- 根目录 `server-secrets` 和 `development-secrets` 存储中的服务商 API 密钥与 OAuth 令牌；
- macOS 钥匙串中的条目；
- 通过 `--tls-cert` 和 `--tls-key` 传入的证书/私钥文件，以及由 Caddy 等外部 TLS
  终止服务管理的文件；
- 所选 Runtime 数据目录之外的存储。

在同一台 Mac 上，恢复后的数据库引用仍可使用该 Mac 钥匙串中依然存在的凭据。换到另一台
机器后，需要重新连接服务商账号。恢复 Server 时，也必须重新配置凭据。无论哪种情况，
外部的 Server HTTPS 文件都需要单独提供。

Server 凭据文件在静态存储上等同于明文，通过仅所有者可访问的文件系统权限保护。在
Linux/Unix 的本地持久化存储上，替换或删除凭据只有在临时文件完整写入、文件同步、关闭、
原子重命名和父目录同步全部成功后才会报告成功。重命名前失败时，已确认的凭据仍可使用。
首次打开时，凭据存储会创建缺失的目录，并同步准确的目录路径及其祖先目录条目，一直
到文件系统根目录；祖先路径中的符号链接指向的实际路径也会同步。每次打开都会重复这些
同步步骤，因此重试也会校验初始化失败后留下的目录。Server 账号需要具备打开和同步这些
祖先目录的权限；Server 数据目录之上的已有祖先目录权限保持不变。新建的目录和 Server
数据/凭据目录仅允许所有者访问。初始化失败时，存储不可用，已经创建的目录可能会留给下次尝试使用。
祖先路径中的符号链接如果指向非规范路径，存储会保持不可用；请使用解析后的数据目录路径。

如果重命名成功后目录同步失败或操作被取消，当前凭据存储会保持不可用，直到重新打开；
文件可能已包含新凭据。请先检查存储健康情况并重新启动 Server，再重试操作。已经发放的
凭据副本保持原有生命周期。这不会把凭据导出到备份，也不保证能从故障存储硬件中恢复。
Windows 的编译兼容性不代表已经验证相同的崩溃耐久性保证。

## macOS App

打开「设置 → 安全与数据 → 证据存储」，选择「创建备份」或「恢复备份」。ViberMate 要求
先停止所有 Capture，会暂停新的本地出站工作，重启本地 Runtime，并在确认前显示准确的
来源目录和新的目标目录。

恢复总是创建一个新的 Runtime 目录，绝不覆盖当前目录。只有清单、每个文件的哈希、
SQLite 完整性、外键和 schema 兼容性全部通过后，App 才会切换到恢复出的目录。如果恢复
出的 Runtime 无法启动，原有的存储选择就是回滚的依据。

## 原生或容器 Server

先停止所有使用该数据目录的 Server 进程。使用本地持久化存储上的绝对路径：

```sh
vibermated backup-data \
  --source='/srv/vibermate' \
  --target='/srv/backups/vibermate-2026-09-26'

vibermated verify-backup \
  --source='/srv/backups/vibermate-2026-09-26'

vibermated restore-data \
  --source='/srv/backups/vibermate-2026-09-26' \
  --target='/srv/vibermate-restored'
```

容器部署时，可以对挂载出来的宿主机数据卷运行这些命令，也可以用一个同时挂载了两个
目录的一次性容器来运行。不要把正在使用的 SQLite 目录放在网络共享或云盘同步文件夹中。

只有 `verify-backup` 成功后，才用恢复出的目录启动 Server。文件缺失或被改动、出现
多余文件、数据库损坏、外键失效或 schema 不兼容时，命令都会直接失败，不会继续。恢复
失败时，现有的 Runtime 目录保持不变，也绝不会替换一个非空或未知的目标目录。新创建但
未完成的目标目录可能会留下来，供检查或手动删除，但 ViberMate 绝不会使用它。

容器部署的数据卷与回滚说明见 [Docker 部署](docker.zh-CN.md)。

## 格式兼容与回滚

继续支持精确匹配的已发布 `vibermate-runtime` 第 1、2、3 版及真实 Standard/Blue/Red
账号偏好，单库公开导出仍为 v1。公开恢复先验证旧复制清单，再持有两个目录锁，仅在新
目标执行存储切换；绝不升级备份来源。原始单库保留为归档，目标同时包含必需的
`vibermate-control/3` 和可选的 `vibermate-observations/1` 布局声明。

分离布局公开导出使用 v2；恢复验证后重现声明的角色布局和事实。当前观察库按停机快照
独立校验，不能用历史维护哈希代替当前哈希。已维护归档须匹配最新证书，并继续保留
未改动的原始来源清单。

旧版本不能将分离布局或 v2 备份用作回滚输入。保留切换前独立验证的私有快照。旧私有
`runtime-schema-upgrade/v1` 快照忠实恢复原始 runtime1/2/3 schema、内容和凭据，之后由
Runtime 接管必要的升级/切换。分离私有快照使用独立严格的 `runtime-schema-upgrade/v2`，
重现所记录布局，不隐式切换，并拒绝未完成的分离存储恢复工作。两种私有格式都不是
未完成恢复导出，也不支持原地降级。

未解决的格式升级 receipt 会阻止正常启动、公开备份和移动。请将它与来源及私有快照
一并保留，等待持有锁的启动流程核对结果；不要删除它来强行启动。公开备份继续遵守上述
排除规则；私有回滚快照保留实际本地凭据文件，但不会导出外部钥匙串条目。详见
[私有回滚快照](deployment.zh-CN.md#私有回滚快照)。
