# M1.0-C0a fixed-client behaviour probe

Date: 2026-08-02
Implementation candidate: `98b693a`
Client: Claude Code 2.1.220, the version the built-in catalog pins
(`/Users/null/.local/share/claude/versions/2.1.220`)

## What this is not

This is a bounded behaviour probe, not packaged acceptance evidence. There is
no `VibeMate.app`, no CaptureRun, no MITM, no local Root, and no production
composition root in this run. A local HTTP server stood in for the
AgentEndpoint and returned exactly the response M1.0-C0a emits. It answers one
question only: does the fixed client survive that rejection.

`cmd/vibermate-acceptance` remains the only source of packaged assembly
evidence, and this file does not substitute for it.

## Question

Does Claude Code 2.1.220 request `POST /v1/messages/count_tokens`, and what
does it do when that request is rejected locally with HTTP 422, the Anthropic
error envelope, and `X-Vibermate-Reason: profile_operation_unsupported`?

## Result: `not_observed` dynamically, `degrades` statically

### Dynamic observation

Two non-interactive scenarios ran against the probe with the client's ambient
credentials replaced by a non-secret placeholder:

| Scenario | Observed requests |
|---|---|
| `--print` simple prompt | `HEAD /api/hello`, `POST /v1/messages` x2 |
| `--print` with a Read tool call over a 1.2 MB file | `HEAD /api/hello`, `POST /v1/messages` x2 |

Both completed successfully (exit 0, expected assistant text returned).
`count_tokens` was never requested, so its rejection was never exercised
dynamically. This is recorded as `not_observed`, not as `passed`. The
interactive TUI and explicit compaction paths were not exercised.

### Static observation

The 2.1.220 bundle does contain the operation. `count_tokens` appears 39 times,
including the beta form `/v1/messages/count_tokens?beta=true`. The call site is:

```js
try {
  ...
  let u = await l.beta.messages.countTokens({ model, messages, tools, ... });
  if (typeof u.input_tokens !== "number") return null;
  return u.input_tokens;
} catch (o) {
  w(`countTokens API call failed: ${o instanceof Error ? o.message : String(o)}`, { ... });
  return null;
}
```

Every failure, including an HTTP 422, is caught, logged, and converted to
`null`. The client is constructed with `maxRetries: 1`. A separate token
measurement path uses `beta.messages.create` with `max_tokens: 1`, which
travels the ordinary semantic `/v1/messages` route and is therefore unaffected
by this Goal.

## Conclusion

The fixed client degrades on the M1.0-C0a rejection rather than terminating, so
the capability is not recorded as `blocked` and the contingency Goal for a
local tokenizer is not required to unblock it. A local tokenizer remains the
correct eventual answer for accuracy, not for availability.

This conclusion rests on a static read of one client build plus two
non-interactive scenarios. It does not cover the interactive TUI, explicit
compaction, other Claude Code versions, or any other client. It must be
re-established through packaged acceptance before any Preview claim.

## Incidental observation

The only uncatalogued request either scenario produced was `HEAD /api/hello`,
which carries no body. Under this Goal's rule it keeps the original-origin
path, so the observed fixed-client control plane is unaffected. A later
connection-policy Goal replaces that narrow exception with an explicit
allow/deny/ask decision.
