# M1.0-C0a fixed-client behaviour probe

Date: 2026-08-02
Implementation candidate: `98b693a`, re-established at `095f3ca`
Client: Claude Code 2.1.220, the version the built-in catalog pins
(`/Users/null/.local/share/claude/versions/2.1.220`)

## What this is not

This is a bounded behaviour observation, not packaged acceptance evidence.
There is no `VibeMate.app` and no production composition root in this run.
`cmd/vibermate-acceptance` remains the only source of packaged assembly
evidence, and this file does not substitute for it.

## Question

On a managed route with no typed `ProfileOperationTarget`, does Claude Code
2.1.220 request `POST /v1/messages/count_tokens`, and what does it do when
that request is rejected locally with HTTP 422, the Anthropic error envelope,
and `X-Vibermate-Reason: profile_operation_unsupported`?

## Managed-route result: `degrades` — the client continues with a local estimate

Observed in the product's own runtime, with a real CaptureRun, a real local
Root, real MITM decryption of `api.anthropic.com`, and the rejection produced
by the shipping admission path. The run is
`TestAFixedClaudeCodeDegradesWhenCountTokensIsRejectedLocallyOnManagedRoute` in
`internal/desktophost`.

This observation is deliberately route-scoped. It does not claim that
`count_tokens` must stay local after an Access explicitly selects the future
system `original_passthrough` profile. That profile is a typed Access route:
its payload-bearing auxiliary operations use `profile_operation`, exact
ClientOrigin and client Auth. It must not be implemented by reopening the
generic `original_origin` auxiliary bypass closed by C0a.

### How the operation was reached

`--print` prompts never request `count_tokens`, which is why the first pass at
this question could only record `not_observed`. `claude plugin details` does:
it prices every skill in a plugin and sends the skill text to do it. The run
builds its own local marketplace and plugin rather than borrowing one from the
machine, so the observation says the same thing anywhere.

Two requests are issued per invocation, both to the beta form the catalog
already matches:

| Request | Body |
|---|---|
| `POST /v1/messages/count_tokens?beta=true` | 234 B |
| `POST /v1/messages/count_tokens?beta=true` | 6,112 B (the skill text) |

### What the client did

It exited 0 and printed the full token-cost table from a locally computed
estimate:

```
Projected token cost
  Always-on:   ~39 tok   added to every session

Per-component (rounded)
  component  always-on  on-invoke
  probe-one       < 20       ~770
  probe-two       < 20       ~770
```

That the number is local, not remote, is a measured difference rather than an
inference. With the same fixture and a stand-in endpoint answering
`{"input_tokens": 999999}`, the same command prints `~999,999 tok` and `~500k`
per component. With the endpoint answering 422, it prints `~39`.

### Why this shows the request arrived and was rejected

The client's printed output is identical whether `count_tokens` is answered
with 422, refused at the TCP level, or answered 401. Output alone therefore
cannot witness the rejection, and this file does not claim it does.

The witness is a mutation. Registering `count_tokens` as
`OperationPayloadControl` instead of `OperationPayloadClientSemantic` — that
is, undoing M1.0-C0a step 2 — makes the same managed-route run send **6,488
bytes** through the generic original-origin path to `api.anthropic.com` and
fail the test's byte ceiling. So in this runtime the client does issue the
operation with kilobytes of its own content, and the step 2 cut is what keeps
those bytes local while no typed managed Profile operation exists. The
mutation was applied, observed to fail, and reverted; the catalog is
byte-identical to its committed form.

## Conclusion

The fixed client **degrades on this managed-route M1.0-C0a rejection**: it
continues with a local estimate rather than terminating. Under design 12 §3.2
step 2 that means the temporary managed capability states `count_tokens` as
`unsupported`; it is not recorded as `blocked`, and the contingency Goal for a
local tokenizer is not required to unblock that route. A local tokenizer
remains the correct eventual managed-route answer for accuracy, not for
availability.

Step 1 only observes the compatibility outcome. It does not authorise the cut,
which stands regardless of what was observed.

Step 3's freeze is `internal/operationcatalog/c0a_freeze_test.go`. Each of its
three assertions was mutation-checked rather than assumed: adding
`client_data` to `AllowsOriginalOrigin` splits the payload bit and fails the
first; registering `count_tokens` as `control` fails the other two. A fourth
assertion was written and then removed for being unfalsifiable — no catalogue
entry can both carry client payload and admit the original origin, because the
two predicates are written as complements.

## Bounds

- One client build (2.1.220) and one command. The interactive TUI, explicit
  compaction, and other clients are not covered.
- No packaged acceptance run. This must be re-established through
  `cmd/vibermate-acceptance` before any Preview claim.
- The degradation is silent to the user. The client reports a local estimate
  with no indication that the endpoint refused, and that estimate differs from
  the remote one by orders of magnitude on the same input.

## Known observability gap

A locally rejected client operation leaves no record anywhere in vibermate.
The rejection is decided before an Exchange ID is allocated
(`internal/loopbackproxy/handler.go:777`), deliberately, so that a request with
no typed handling plan cannot place client payload in a buffer that outlives
the decision. The consequence is that nothing in the runtime can answer "did
the client ask for this and get refused" — this file had to answer it by
mutation instead.

Closing that gap belongs to design 12 §3.2 step 4, which introduces the typed
`ClientOperationRun`. Adding a record now would run ahead of the fixed order,
so it is recorded here rather than built.

## Incidental observation

The only uncatalogued request the run produces is `HEAD /api/hello`, which
carries no body. Under this Goal's rule it keeps the original-origin path, so
the observed fixed-client control plane is unaffected. A later
connection-policy Goal replaces that narrow exception with an explicit
allow/deny/ask decision.
