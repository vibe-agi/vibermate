# 长会话与证据读取隔离设计

日期：2026-10-06。状态：三份只读方案已比较，本文待用户审阅；不是已实施或已通过性能验收的声明。

父计划：`../plans/2026-10-03-production-readiness.md`。实施时以 Global Egress Task3 独立审查后的实际接口和源码为基线，不与其并发修改源码。本设计不缩减 MCP、CA、客户端、持续运行或发布范围。

## 用户要求与验收目标

正常的长任务应持续运行，用户不需要数消息、换账号、重开会话或因为 ViberMate 自身性能问题处理警告。阅读历史、打开工具返回和查看图片不应拖住其它任务的心跳、审批或请求。

用户已明确允许必要重做内部模块、接口和未发布格式，不必为假想老用户维持不合理兼容。优先选择职责清楚、可测量和可验证的实现，不叠加长期兼容分支。此授权不等于可以删除当前开发者的账号、配置和会话；已有真实数据继续经过备份、迁移及恢复验证保留。

“无感”不是隐藏错误：真实的上游拒绝、权限撤销、磁盘耗尽、记录损坏必须如实处理。它要求在声明支持的正常工作负载下，不再因内部条数限制、全文物化、慢查询或长事务破坏使用流程。不得静默裁剪、总结、遗漏请求历史或伪造完整记录。

## 已确认的事实与未确认的因果

- 用户指定会话的三次合法约4MiB请求，经与0.1.23相同的实际 codec 离线重放，均因内部 neutral Request 的4096条消息上限失败。没有对应模型上游尝试；继续/恢复同一会话仍携带同样历史。该限制仍存在于当前开发分支。
- 请求解析和展示投影共用这一消息数校验；存储和分页总数有不同容量。只修改一个常量不能证明转发、变换、记录和阅读都正确。
- Raw 元数据列表先加载、解压全部正文，再丢弃正文返回摘要。正文分块查询在索引列上调用hex，实际只读查询计划显示扫描；该仓库与 Capture 心跳共用单个写连接。
- 正文分块、散列和压缩还发生在部分写事务内，读写隔离不能只改一个查询。
- 上述读取耦合是已证实的缺陷机制，但还没有在隔离真实 Store 中复现现场全局心跳中断的完整时序，不能宣布已经证明或修复。
- 当前 managed 路径可能在完整 decode 前取得 Account 凭据；“没有模型上游尝试”不能外推成“没有任何凭据准备或刷新”。新的处理顺序必须明确验证。

详细私有诊断、命令与脱敏结构指标保存在主计划 scratch；真实请求正文不进入测试、文档或提交。

## 方案比较与选择

方案 A 从调用者出发，统一执行与证据读取的高层职责；方案 B 对比同库隔离、独立 payload SQLite 和自定义 journal；方案 C 从正常同协议请求出发，使用完整验证的不可变 RequestDocument。

采用 C 的请求文档边界，结合 A/B 的证据职责隔离。保留现有 Runtime 对权限和生命周期的所有权，不为了减少方法数量增加空转发 facade。现有协议和证据模块可以直接替换不合适的内部接口。

首先在现有 SQLite 上实现正确的元数据契约、索引读取、独立有界读资源及短事务；以真实并发和故障结果判断是否仍需拆分 payload 存储。现在不引入自定义 journal，也不预先制造跨库提交、GC pin、双库备份的复杂度。若实测仍达不到控制链路隔离目标，必须在同一用户体验目标下修订存储实现，而不是用警告或更长超时验收。

## 一、请求文档不再等于展示对象

协议模块拥有一次请求的不可变原始字节、完整验证状态、紧凑条目索引及执行必要事实。正常入口不以完整 `protocolcore.Request.Messages` 数组作为唯一合法表示。

这里针对已识别的MODEL协议请求；原始账号GET、其它非语义转发、盲隧道和原生MCP仍遵循各自已授权契约，不强行当作MODEL JSON解析，也不因此新增可访问目标。

文档不是发送权限。Capture、Environment、Client Flow、真实 Account 租约、冻结出口、Offline 准入、ToolDecision 和 once/receipt 继续由现有权威模块签发与检查；不能从文档、数据库历史或 operation ID 重建。

整个请求须在发送前完成相应协议契约的校验，包括尾部条目、嵌套结构、重复/大小写冲突字段、工具定义、协议标志及跨项关系。不能找到model后就跳过余下历史。原样、compatible同协议和跨协议的合法输入集合分别定义，不用一个宽松开关放开存储执行、后台执行或未知目标。

同协议且无正文变更时，发送经过完整验证的原始文档；账号替换只改变依法选定的认证上下文，不重建或删减历史。模型映射等明确变更生成新的、已验证的文档版本，保留原入站与实际出站证据的区别。

需要语义处理的消费者通过有界迭代/窗口读取完整历史。一个wire item可能产生多个语义项，也可能贡献工具定义等非消息事实，索引必须准确表达，不能假设input数量等于消息数量。

## 二、保留全部已配置能力

Account Selector 必须得到其契约定义的完整请求和冻结 Account Set；不能因请求长改选默认账号或只给最近一段。正文/响应变换保留完整输入、Turn Context 和原有禁止修改目标等约束。变换输出重新完整验证；失败不能偷偷退回原请求。

跨协议转换遍历全部可移植消息、工具调用及返回，保留顺序与关联。对无法移植的提供者私有状态使用明确的原有语义，不丢失后仍宣称完全等价。不得重新收集到另一个小固定容量数组，把同样限制移到下一层。

脚本的全量字符串/对象开销必须计入真实资源预算。现有执行时长限制不自动等于硬内存限制；规划时单独验证实际脚本引擎的可强制取消和内存隔离。若现有进程内实现不能证明所需界限，选择满足同一权限与平台约束的内部执行适配器，不能省略已配置脚本来通过长会话测试。没有凭据、网络或文件权限扩张。

历史工具记录不是新工具执行。新的响应工具意图仍在真实审核通过后才能交给客户端；原生 MCP 的原登录、每profile默认关闭、防重复执行和恢复凭据不由本次 MODEL 文档设计替代。

## 三、三种工作分别承担自己的成本

1. **执行必要事实**：当前权限、实际路由/账号/出口、审批与一次执行消费、物理尝试和真实终态。这些继续满足发送前或终态所要求的耐久性，不能异步成“先发后补权限”。
2. **保留证据**：按冻结记录策略准许保留的不可变字节、关联、摘要、保留期限和耐久进度。入队不是已落盘；未知提交不是失败后可以重发。
3. **阅读投影**：对话分页、预览、索引和展示关系。它们可从仍有权限且未过期的证据重建，不能成为正常发送的先决条件，不能猜测缺失正文或恢复执行权限。

请求转发不等待为了界面生成的全文对象、搜索索引或页面加载。需要保证证据落盘的现有终结 fence 继续等待真实持久结果，但等待时不占住心跳/审批所需的数据库连接和权威锁。

投影尚在整理时显示已有内容和正常加载状态，不将整理延迟标成记录丢失；真实丢失仍明确区分。完整记录、metadata-only和Off的含义保持：不得为实现懒加载，默认把原本不应保留的正文存到磁盘。

## 四、阅读模块只为当前阅读付费

元数据列表从数据库只取元数据，使用独立类型和元数据校验，绝不以伪造的空Body通过`StoredEnvelope.Validate`。列表和普通翻页不读取、解压或散列其它正文。

正文或图片仅在实际打开时读取所需记录/页，使用原始digest键的索引查找、有界批次、稳定的文档版本和准确游标。SQL读取结束后释放连接，再进行可取消的解压和内容处理。不能用全库扫描完成单条证据读取。

读取走已有有界只读资源，心跳、权限变化和必要审计保留短写事务。散列/分块/压缩不占用控制写事务；批量写入及回收需有明确的事务工作量和取消界限。只读连接不能无限增加，长快照不能无限钉住WAL。

正文揭示仍须范围授权、到期检查、真实完整性校验和相应揭示审计；摘要游标不授予正文权限。取消当前页面只撤销当前读取，不影响其它Capture。并发删除、过期和读取的顺序要有精确语义，不延长同意的保留期限。

## 五、资源控制不变成用户的日常操作

不把4096简单换成另一个业务消息条数上限。分别核算原始字节、解码/解压、紧凑索引、跨项状态、同时存活的文档版本、脚本、转换输出、证据队列及页面渲染资源。

先保留一份有界的内存原始文档，避免重复完整JSON/neutral/脚本对象拷贝。当前16MiB输入、32MiB记录以及页面限额只是测量基线，不代表把它们乘在一起后的分配被允许，也不直接将存储100001条容量当新业务限制。

在分配前预留资源、限制并发并公平调度，取消和结束后释放。完整合法请求的累计条目数不决定页面大小；多任务也不能无界叠加每请求上限。支持范围内的正常长任务不应触发内部资源警告。真正的畸形输入、恶意结构或设备资源耗尽不得靠无限排队、丢弃尾部或伪造完成解决。

详细计划先包含隔离测量任务：实际解析/索引/克隆与脚本开销、并发峰值内存、控制延迟、读写事务占用、取消回收和WAL趋势。数据决定准确的内部预算及调度参数，不能凭一个新常量宣称容量问题已解决。若需要将Off/metadata-only请求正文持久化为处理临时文件，这是新的隐私选择，必须另行取得授权；本设计没有批准。

## 六、验收必须覆盖用户场景

- 使用合成的4102/4111条、约4MiB真实管线请求重现原失败，再覆盖显著更长但合理的数据量，以及多小条目、大工具返回、图片、嵌套和末尾非法项；完整发送与内容/顺序校验，不使用真实私有正文。
- 原登录同协议、账号替换、模型映射、完整Account Selector、请求/响应变换及已支持跨协议路径分别验证；选择或修改依据放在历史尾部，证明没有只处理前缀。
- 真实审核、拒绝、取消、账号/出口冻结、一次发送和原生工具隔离保持。协议拒绝不能触发换账号重试或工具POST重发。
- 完整内容经过实际Store和分页界面往返；所有页面能重建完整已获准保留的历史，单页/渲染树仍有界。Off和metadata-only不得泄露正文。
- 在真实临时Store上，证据列表的正文读取/解压次数必须为零；正文查找随选中内容规模增长，不随整个库规模扫描；取消后连接/worker/WAL资源按界限回收。
- 同时进行真实Capture心跳、模型/工具操作、写入、阅读和留存回收，测量等待、事务占用、p95/p99和失败。慢正文处理被受控阻塞时，独立心跳/审批应在释放它之前完成。不能加大5秒心跳或10秒UI超时来使测试通过。
- 记录和验证提交不确定、磁盘故障、损坏、进程退出、恢复及备份边界；未落盘不能标已记录，重建阅读索引不能重发网络请求。
- 中英文、窄屏/大字体、分页/图片加载、离开页面取消与晚到响应，均按正常用户流程检查，不把内部状态管理交给用户。

## 交付与范围控制

设计落定后拆为独立可审查的实施单元：隔离性能与资源证据；请求文档及必要消费者；证据读取/写入隔离与界面；最后完整并发和用户流程验证。具体接口、数值和每项测试在详细计划中由实测与实际调用方确定。

不推倒已验证的账号、权限、MCP一次执行和恢复权威，只替换造成耦合的接口与实现。新代码不保留无人需要的旧内部执行路径；当前真实数据通过验证的升级保留。任何新物理存储方案必须补齐故障、GC和备份协议后才能启用。

完成本设计不等于整个生产Goal完成；最终仍需同一源码的完整客户端矩阵、CA、持续运行、独立整体复核、签名公证及GitHub/Homebrew交付。

## 自检

覆盖已确认消息限制、投影耦合、元数据正文物化、非索引查询、读写连接共享及事务内重处理；区分已证实机制与未复现现场因果。完整历史、策略能力、权限/一次执行、Off/metadata-only和真实数据保留均有对应验收。没有将警告、更长超时、旧用户兼容或无限资源作为正常体验的替代。尚未测得的资源参数被明确放入前置实测任务，不能由实现者任选一个上限结案。
