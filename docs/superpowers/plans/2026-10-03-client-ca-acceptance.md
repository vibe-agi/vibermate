# Client CA Acceptance Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Establish execution-level CLI behavior and actual native client CA installation evidence for Task 8 from one clean candidate SHA.

**Architecture:** Keep the existing authenticated public-CA download and native trust adapters. Add private per-invocation dependencies for deterministic CLI tests, then exercise the compiled production CLI against a synthetic Server in disposable native environments. A narrow manually dispatched workflow produces independently checked, credential-free evidence.

**Tech Stack:** Go 1.26.8; existing Go standard library and repository packages; Node.js 22.23.1 for evidence/workflow checks; Debian and RHEL native trust tools; hosted macOS 15.

**Spec:** `docs/superpowers/specs/2026-10-03-production-readiness-design.md`, parent Task 8 in `docs/superpowers/plans/2026-10-03-production-readiness.md`, and `.superpowers/sdd/2026-10-03-production-readiness/release-resource-preflight.md`.

## Global Constraints

- Controller-reviewed Task 8 subplan. Execute tasks serially with TDD and independent review; native installation is authorized only in the explicitly admitted disposable environments. Production release still requires all parent-plan gates.
- Go toolchain 1.26.8; retain `go 1.26.0`. No new runtime dependencies or SQLite schema changes.
- CI Node.js 22.23.1. Flutter is unnecessary for this pure-Go gate; any later App build retains Flutter 3.41.5 revision `2c9eb20739dfec95e2c74bd3dfa4601b0a8a36aa`.
- English and Simplified Chinese messages change together. Certificate fingerprints are deliberately shown for CA verification; never show tokens, passwords, private keys, recovery keys or unfiltered server/native errors.
- All fixture credentials, certificates and state are synthetic and temporary. No user login/configuration, live providers, external tool calls or production service directories.
- Native Linux installs run only inside disposable Docker containers with **no host mounts**, Docker socket, host home/CA mounts, privileged mode or host network.
- Native macOS installs run only on a fresh GitHub-hosted `macos-15` VM. Changing `HOME` isolates CLI state, **not** the user's keychain; never run this gate on the shared local Mac or an existing self-hosted user.
- macOS operation stays `/usr/bin/security add-trusted-cert -r trustRoot -p ssl <root.cer>` in the current-user domain. No `sudo`, `-d`, system keychain override or admin-domain substitute.
- No test TLS bypass, fake verification, mutable package globals or public test-only product API. A successful install must be followed by fresh-process system-root verification.
- Ordinary `go test ./...` can explicitly skip the opt-in native test. With `VIBERMATE_CA_ACCEPTANCE=1`, missing inputs, unsafe environment, authorization failure, timeout, failed verification or cleanup are **failures**, never skips or successful evidence.

## Current evidence and file boundaries

`cmd/vibermate/ca.go` parses action/target/consent, obtains the default remote state directory, calls `runlauncher.RemoteRootCertificate`, validates the public CA, rejects a supplied mismatch before printing identity or installing, writes download with `O_EXCL`/0600, and calls `desktoptrust.InstallClientCA`. Its current tests cover parsing only; many messages are hardcoded English and raw errors are printed.

`internal/desktoptrust/client_ca.go` checks current trust, creates temporary public certificate material, calls the platform installer with a two-minute limit, and rechecks trust. Linux selects Debian `update-ca-certificates` or RHEL `update-ca-trust`; macOS uses the exact current-user command above. `internal/serverhost/runtime_root_ca_integration_test.go` already proves ordinary-client public download, unrelated-management denial and revocation. Reuse its `serverOptions`/`shutdownServer` fixtures but do not reuse its insecure `tlsHTTPClient` in new acceptance.

The existing release workflow uses `macos-15` and Xcode 16.2. Official runner documentation says normal hosted jobs use a fresh VM; the inspected arm64 image lists Xcode 16.2/16C5032a. This supports an actual bounded attempt, not a claim that headless current-user authorization succeeds. Sources: [hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners), [macOS 15 arm64 image](https://github.com/actions/runner-images/blob/main/images/macos/macos-15-arm64-Readme.md).
