# ViberMate 0.1.30 (32) — Daybreak and native Codex continuity

Adds managed account Cyber Access preferences and native Codex model-directory and turn-state behavior, with focused startup, evidence-reading and workbench reliability fixes.

- Accounts offer Standard, Daybreak Blue and Daybreak Red. Existing accounts default to Standard; older clients that omit the setting preserve it. Blue/Red require the final selected model to advertise the chosen grant. An unavailable grant fails explicitly without another mode, account or retry fallback.
- Exact native Guardian requests derive Blue from a frozen Red account preference without changing that account. The actual final model must advertise Blue. Standard performs no capability lookup.
- Native model-directory reads use the selected managed account, a closed bodyless request with validated `client_version`, bounded complete metadata, model aliases and account/route-scoped ETags. Original forwarding keeps its own credential boundary.
- Model aliases rewrite only the exact mapped model; genuine server reroutes remain visible. Both `openai-model` and `x-openai-model` survive the narrow native response-header allowlist. Recorded upstream evidence retains the actual provider identity.
- Native turn-state continuity stays bounded in memory across eligible account switches, with scope, ownership, cancellation, expiry and shutdown checks. New direct turn-state header recordings redact token values at ingress, provider and transform boundaries; live forwarding and translated token bytes remain exact, including with recording disabled or failing.
- Raw chunk reads keep the indexed digest lookup as unrelated history grows. Initial local/remote Run and ACP attachment defaults to 30 seconds; routine heartbeat and finish keep 5 seconds, Capture creation keeps 90 seconds, and explicit control timeouts remain effective.
- Control failures report safe stage/reason details. Workbench control calls have a total 30-second deadline across headers and body, cancel their own request and leave concurrent requests usable. A timeout may have completed a mutation: refresh and check the result before deciding to retry.

## Upgrade and rollback boundary

This version introduces monolithic `vibermate-runtime` revision 3 for the canonical account preference. Published v1/v2 definitions remain unchanged. Guarded startup upgrades 1→2→3 or 2→3, verifying a complete private snapshot before each separate transaction and proving all existing v2 fields and sequence values. Both stages retain data/server ownership and share one bounded work budget; normal writers start only after a known durable revision 3 result and receipt removal.

New readers support exact revisions 1/2/3, and current revision 3 backups preserve real Blue/Red preferences. Older releases refuse revision 3 unchanged. Rollback restores the verified pre-transition private snapshot into a new directory at its original format; there is no in-place downgrade. Public backup exclusions remain unchanged. See [backup and restore](../backup-and-restore.md) and [private rollback snapshots](../deployment.md#private-rollback-snapshots).

The existing monolithic recording architecture remains; optional recording can still contend with control work. The separate storage-isolation release is not included. Update the App/CLI and Runtime Server as appropriate; publishing software does not deploy or restart a remote Runtime.
