# ViberMate 0.1.24

Release preparation for App/Runtime/CLI `0.1.24+26`. Publication, signing, notarization, download verification and Homebrew update remain pending the protected candidate gates.

## Highlights

- Continue an existing long capture without dropping its history at the former 4096-item boundary. The reviewed hotfix carries a same-session request history past 4111 items, preserves the final response tail and keeps the complete record readable after close and reopen.
- Keep the desktop control session usable for the adopted 10-day lifetime, including renewal while the App is hidden while the computer is awake. A lost renewal response is retried with the same idempotency key; writes are not replayed automatically.
- Verify native same-session continuation with the official Codex CLI 0.160.0 macOS arm64 package. The continuation keeps the original thread, ordered history and final sentinel without compaction or a fork.
- Open existing v0.1.23 schema-revision-1 data in the candidate, continue the original capture, and preserve old rows, content hashes, usage and capture relationships. The verified upgrade uses a separate post-upgrade backup and never overwrites the pre-upgrade backup.

## Upgrade and rollback boundary

- Finish or stop active Captures, make a verified offline Runtime backup, then update and restart both the App and deployed Server/Runtime as applicable. The upgrade does not restart active sessions automatically.
- The candidate preserves existing schema-revision-1 data and does not rewrite retained evidence. Backup archives contain database data and references, not provider credential stores or keychains; keep the existing credential and trust setup available separately.
- An older v0.1.23 binary can read the ordinary rows from the pre-upgrade backup. It explicitly rejects the candidate-only long-history and framed-response rows, so downgrade by restoring the pre-upgrade backup into a separate directory; never replace newer history with an in-place rollback.
- This scoped hotfix does not claim MCP compatibility, default-egress changes, terminal-display changes, or the later full production-readiness matrix.
