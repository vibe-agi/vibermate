# 启动上下文、运行概览与用量报表 review

日期：2026-09-28。代码基线：`09a01d7`。本轮为代码审查、隔离规模测量和设计建议，尚未修改业务实现。

## 结论

Git 信息已经通过创建运行记录的同一个 `POST /api/v1/capture-runs` 上报。应当收敛启动上下文的采集、验证和持久化，不增加 Git 专用上报接口，也不把项目/分支放到长期设备资料中。

当前报表存在可复现的规模问题：汇总受明细条数上限影响、查询占用请求落库使用的数据库连接、多维结果可能超过客户端响应限制。截图中的概览则是客户端分页窗口的即时计数，尚不是完整的会话/运行统计。建议先修正数据查询与口径，再实施页面调整。

## 发现（按优先级）

### P1：超过 100,000 条时，总量和趋势一起被截断

位置：`internal/runtimeusage/projector.go:268`、`internal/runtimepersistence/runtime_usage.go:240`。

每次报表先读取时间范围内最近的最多 100,000 条 Observation，然后在 Go 中计算所有总量、费用、日趋势和分组。上限发生在汇总之前，因此较早的请求会从整个报表消失。`truncated` 提示同时混用“原始记录不完整”和“分组明细不完整”，无法说明哪些数字可信。

隔离数据库有 100,001 条时，报告总调用数为 100,000。提高上限会扩大内存和连接占用，并不能解决口径。

修正方向：完整范围内的总量与趋势独立聚合；限制只作用于展示的分组页。分页应返回后续游标和完整小计。不存在未采集历史时，不因 UI 明细分页把总量变成下限。

### P1：报表扫描阻塞共享连接，完成记录存在静默丢失风险

位置：`internal/runtimepersistence/store.go:105`、`internal/runtimepersistence/runtime_usage.go:229`、`internal/productruntime/builders.go:729`、`internal/exchange/pipeline.go:1070`。

SQLite 连接池只有一个连接。`ListUsage` 在持有查询游标期间反序列化并验证每一条 JSON，整个过程独占该连接；查询开始还会执行过期清理。请求完成时，Activity、客户端身份和 Usage 依次写入，整段观察共用 2 秒预算；最外层忽略 `ObserveTerminal` 返回的错误，没有持久重试机制。

实测 100,000 条扫描期间，一条很小的写操作等待约 0.67 秒。这个结果证明读写相互阻塞；它不证明用户此前的流中断由报表引起。较慢磁盘、更大记录或并发报表可能耗尽完成记录预算，造成缺失统计，不能将这一风险表述成已复现的历史故障原因。

修正方向：报表读路径不做清理写操作，过期处理进入现有维护流程；缩短数据库持有时间，使用独立只读连接承担报表查询，并验证 WAL、备份、离线维护和关闭流程。完成 Activity 与用量记录尽量在同一短事务中提交；无法提交时必须保留可观测的失败/缺口状态。不要用无界异步队列隐藏问题。

### P1：服务端允许的报表会被客户端 16 MiB 上限拒收

位置：`internal/runtimeusage/projector.go:287`、`ui/flutter_app/lib/core/api/control_api.dart:451`。

每次返回六个维度的完整层级树，每个维度各允许 5,000 个节点，另外还有用户、上下文和会话明细。服务端没有与客户端对应的总字节预算。

30,000 条多分组数据形成 27,001 个节点，短名称时响应为 13.50 MiB；使用仍符合现有校验的较长名称时为 17.62 MiB，超过客户端 16 MiB 的读取限制。用户此时收到报表加载错误，而不是可翻页的明细。

修正方向：首屏返回概览、趋势与当前维度第一页；展开一行才查询这一行的下一层。沿用一套带过滤条件的聚合查询，不为每个维度建立独立实现。限制节点数、单页行数及响应字节数，父层总量独立于当前页。

### P2：每 5 秒重算整个报告，并扫描与期间无关的历史运行

位置：`ui/flutter_app/lib/features/workbench/workbench_controller.dart:748`、`:1003`、`:1425`、`internal/runtimeusage/projector.go:251`、`:434`。

可见报表页跟随全局 5 秒轮询。每次都读取最多 10,000 条历史运行，重新扫描用量、逐请求计价并生成所有层级；同一 Controller 内有请求合并，但多个 App/Web 查看者仍会各自重复执行。`quiet` 刷新进入 `refreshUsage()` 后仍执行 loading 通知与整个报告替换。

读取运行列表还复用了面向界面的最近活动排序。该查询包含 Activity 关联计算，最多逐页调用 50 次。即使所选期间没有请求，10,000 条过期历史运行也让空报告耗时约 0.42 秒，并触发 `truncated`。

修正方向：统计仅查询范围所需的归属，不为每次报表加载整个运行目录；新记录已经冻结的归属应直接使用。增加基于用量数据变化、删除/留存变化和价格快照的缓存失效，多个查看者合并相同作用域查询。UI 在数据无变化时保留当前视图，刷新保留展开状态。缓存键必须包含权限作用域、日期和时区，不能只按 URL 或日期共享成员结果。

### P2：当前概览随翻页变化，且混淆运行与会话范围

位置：`ui/flutter_app/lib/features/workbench/captures_view.dart:946`、`ui/flutter_app/lib/features/workbench/workbench_controller.dart:3231`、`:3300`。

概览直接对 `selectedActivities` 计数；初始页为 100 条，加载更早记录会改变“总数”。实时窗口还存在保留上限，数字并非稳定累计值。总数计入 `pending`，分项却只列成功、失败和取消，能够解释截图中 100 与 94 + 2 + 3 相差一次的现象。

当有精确客户端会话身份时，活动查询会跨 Capture 读取同一会话历史；顶部运行轮数则属于当前 Capture。两者范围不同，却没有在概览里明确展示。概览入口又依赖“已加载终态请求是否都没有正文”，有正文和没正文的运行缺乏统一入口。

修正方向：概览从服务端获取所选范围的完整汇总，独立于请求列表分页。明确“当前会话/本次运行”范围，显示进行中状态。Token 与费用只能来自已采集用量，统计关闭或部分覆盖时显示缺失与覆盖情况，不能根据 Activity 数量补造。

### P2：启动信息已有统一请求，但采集组织与项目身份仍需收敛

位置：`internal/runlauncher/launcher.go:172`、`internal/runlauncher/acp_unix.go:52`、`internal/runlauncher/git_snapshot.go:19`、`internal/runtimeusage/groups.go:23`。

普通启动依次组装环境变量名称清单、运行元数据、客户端目标事实，再补入 Git；ACP 路径重复组装运行元数据和 Git。两者均通过创建 Capture 上报，并没有 Git 的第二次网络上报。Git 采集内部使用进程 `os.Environ()`，其他采集器使用 Launcher 的 `BaseEnvironment`，输入来源也不完全统一。

项目键目前由 Git common-dir 绝对路径及 MachineID 导出。它能区分同名的无关仓库，却不能把团队在不同设备上的同一远程仓库合并。

修正方向：收敛一个具体的启动上下文采集函数，让普通 Run 与 ACP 使用同一份输入和数据结构，之后通过既有创建请求一次提交。Git 从本地配置解析规范化仓库身份；仓库身份与本机克隆身份分别表达。采集只用于归属，登录用户与设备授权仍由 Runtime 验证。

### P2：展开表格与 JSON 解析在前台重复承担大结果成本

位置：`ui/flutter_app/lib/features/workbench/usage_dashboard_view.dart:857`、`:1092`、`ui/flutter_app/lib/core/api/control_api.dart:2537`。

客户端一次解析整个报告；`DataTable` 构建全部已展开行，没有分页或按可见区域构建。较大的顶层列表即使不展开也会全部构建。这里目前只有代码证据，未在真实 App 上测量帧耗时，因此不报告具体掉帧率。

修正方向：先减少网络结果和单页行数，复用 Flutter 的分页/惰性列表，保留稳定行键与展开状态。不要先引入新表格依赖，也不要只把 JSON 解析搬到另一个 isolate 而继续下载整棵树。

## 隔离测量

使用当前生产 SQLite Store、`ListUsage`、Projector 和逐请求计价器；合成数据仅写入临时数据库。价格目录为内存固定数据，无联网。主要规模测量中用户和运行目录为空，以隔离账本/分组开销；运行目录开销另外测量。以下为一次诊断运行的结果，不是生产容量承诺，未包含 HTTP 传输与 Flutter 绘制。

| 数据场景 | 报表生成 | 单次累计分配 | 报表 JSON | 结果 |
| --- | ---: | ---: | ---: | --- |
| 1,000 条，普通分组 | 8.4 ms | 7.05 MiB | 0.90 MiB | 总量完整 |
| 10,000 条，普通分组 | 82.9 ms | 67.27 MiB | 2.73 MiB | 总量完整，部分分组触及节点上限 |
| 100,001 条，普通分组 | 798.7 ms | 667.40 MiB | 2.79 MiB | 只计算最近 100,000 条 |
| 30,000 条，多分组 | 252.6 ms | 204.71 MiB | 13.50 MiB | 27,001 个节点，部分明细截断 |
| 30,000 条，多分组、合法长名称 | 362.4 ms | 293.28 MiB | 17.62 MiB | 超过客户端读取上限 |

“累计分配”是 Go `TotalAlloc` 的单次增量，不是常驻内存或峰值。100,000 条读取阶段约 695 ms，同期小写操作等待约 668 ms。空期间查询在 1,000/10,000 条历史运行时分别约 9/416 ms。

## 统一启动上下文

复用既有创建运行记录的 Interface，使用一个具体数据结构组织采集结果。无需通用 telemetry 框架、采集器注册系统或新的协议版本。

| 内容 | 产生位置 | 归属与用途 |
| --- | --- | --- |
| 设备标识、设备名 | 注册/连接阶段 | 稳定设备身份，运行时引用 |
| Runtime 用户与登录会话 | Runtime 验证连接 | 可信调用者归属，CLI 名字不能覆盖 |
| 本机显示用户名、OS、架构、时区 | 启动器统一采集 | 本机展示元数据，不作为认证 |
| 工作空间、Git 仓库、启动分支 | 启动器统一采集 | 本次启动的不可变项目快照 |
| 环境变量名称清单、允许的客户端目标事实 | 启动器统一采集 | 沿用各自的允许字段与保存期限 |
| 请求状态、模型、Token、时间 | Runtime 请求终止记录 | 从真实请求观察，关联同一个 runId |

采集、传输和验证集中在启动路径。保存时仍遵循事实各自的用途与期限：环境变量名称清单不应因为合并采集就变成长期保存的变量值。

项目身份：本地解析 `origin`，去掉凭据等敏感部分，规范化可确认等价的 HTTPS/SSH 表达，使用 `host/owner/repo` 的稳定标识跨机器分组；只输出安全显示名和不透明标识。无法识别远程仓库时回退本机克隆身份。Fork、SSH 别名和不同域名不按仓库同名自动合并；确有需要时提供显式项目映射。分支保持“启动分支”含义，不用报表查询时的当前分支覆盖历史。

同一团队汇总以连接同一个 Runtime 为前提。各自独立运行的本地 App 数据不会自动跨 Runtime 汇集。本机用户名相同也不能据此认定是同一个成员。

## 概览与团队报表的页面方向

概览面向正在检查 Agent 运行的使用者，首屏回答：选中范围内用了多少、完成情况如何、主要成本和异常在哪里。沿用当前 Flutter 主题与组件，重点放在可核对的数字，不增设装饰性大图。

```text
概览   请求记录                      范围：当前会话 ▾   已更新 …
所属项目 · 启动分支 · 调用者          （只列当前范围内可确认的上下文）

请求数       完成成功率       输入 / 输出 Token       API 等价费用
└─ 成功 / 失败 / 取消 / 进行中 状态构成

请求与失败趋势                       模型用量 / 费用构成

异常类型             次数             最近出现          查看请求
上游连接失败           2                …                 →

统计覆盖与计价覆盖；完整、未知、部分下限有明确区别
```

- 当前会话与本次运行使用显式范围；会话跨多次启动时显示覆盖多次运行，不能暗示都是当前分支产生的。
- 概览入口不依赖正文录制；请求明细仍保留原有分页与技术诊断。
- 请求总数可包含进行中；完成成功率建议统一为成功 /（成功 + 失败），取消和进行中单列，全局报表同步采用同一口径。零分母显示 `—`。
- Token 区分未缓存输入、缓存读取、输出；推理 Token 已包含在输出时不得重复累加。费用保留 API 等价估算和计价覆盖。
- 耗时可作为次级指标，在确认准确起止字段后展示 P50/P95；不从总耗时推算首 Token 延迟或生成速度。
- 异常按次数排序，用可读名称并链接过滤后的请求列表；技术码留在 tooltip/详情。
- 团队项目明细默认“项目 → 调用者 → 模型”，分支作为过滤/可切换的下钻维度，以便同一成员跨分支的消耗先有小计。“参与者”取所选期间真实有请求的身份数；运行进程存在不等于正在开发。
- 数字右对齐、tabular figures、明细千位分隔、概览 K/M、费用有明确 USD 单位；父层与总计不随展开重复相加。390 px 下主指标换行，明细保持可访问的分页与横向滚动。
- 沿用画布 `#10151A`、面板 `#182028`、分隔 `#303C47`、正文 `#F1F5F8`、数据蓝 `#75B8F0`、警示黄 `#E5B663`；标题/正文系统字体，数字等宽特性。页面的主要结构特征是请求状态构成与可核对的小计。

## 改造次序与验收

1. **统一启动上下文与稳定项目身份。** 普通 Run/ACP 共用采集，创建请求统一验证；运行期只引用这份快照。测试相同仓库不同目录/机器、SSH/HTTPS、worktree、无 remote、采集超时与凭据净化。
2. **建立完整汇总与按需明细查询。** 复用现有 SQLite 和 runtimeusage，将查询需要的维度、数值和已知状态放到可聚合的列；总量不受明细上限影响。按范围/权限/当前维度分页，避免查询所有历史 Capture。现有 v1 契约收敛修改，本机已有数据通过明确转换保留。
3. **处理读写竞争与失效刷新。** 短写事务、独立报表读取、已有维护流程负责过期清理；数据变化/价格变化后失效，稳定数据不重复重算。保留现有精确逐请求计价语义：阶梯价格、未知 Token、逐请求舍入不能退化成“按模型总 Token 乘单价”。是否需要日汇总表应由调整后的实测决定。
4. **用同一统计口径提供概览。** 全局、项目/成员和运行/会话范围共享查询与数值表达；Activity 状态覆盖和用量采集覆盖单独说明。关闭正文录制不影响已开启的用量采集；关闭用量采集时不追溯补造。
5. **规模与交互验收。** 至少覆盖 100,001 条完整合计、30,000 条多分组合法长名称、并发读写、两个查看者、成员权限隔离、删除/到期/价格更新失效；验证分页前后总量相同、首屏结果有字节上限、刷新保持展开和选中范围。再测 100 万条的索引聚合，按结果决定是否需要进一步预聚合。

本轮保留现有 v1，不新增报表数据库或消息队列。权限隔离、未知值语义、请求去重、删除/留存及计价精度是重构验收条件。
