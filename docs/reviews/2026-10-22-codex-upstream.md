**1. Injected configuration can disappear at the subcommand boundary (P1).**

ViberMate builds `model_provider="vibermate"`, its destination, env-key authentication, and HTTP transport as root-level `--config` pairs (`internal/runlauncher/codex_provider.go:90–102`), then prepends them to the original child arguments (`internal/runlauncher/launcher.go:303–340`). Arbitrary nonreserved `--config` options remain legal in the invocation grammar (`internal/runlauncher/codex_isolation.go:203–215`). The same placement is used for an explicit native base override (`internal/runlauncher/invocation.go:32–52`). Stable Codex uses Clap's direct parse, and the current main fix explains that a deeper global argument replaces earlier values instead of appending them. [Stable parse](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/cli/src/main.rs#L1038-L1064), [upstream fix 38da85f / #56022](https://github.com/openai/codex/commit/38da85f49e0ab8247d1840f7437ce06fd12d7856), [fixed collection logic](https://github.com/openai/codex/blob/342ed69a174c206c1de52a59491b131e0753cfa5/codex-rs/cli/src/config_override_args.rs#L10-L32).

Reproduction used the installed native binary, verified as `codex-cli 0.163.0`, with temporary `HOME`/`CODEX_HOME`, synthetic credentials, and `sandbox-exec` **denying all network**. It supplied ViberMate-shaped provider overrides for `audit_fixture` before `app-server --stdio`, then requested `config/read`:

| Invocation suffix | Effective `model_provider` | Fixture provider retained | Reasoning override |
| --- | --- | --- | --- |
| `app-server --stdio` | `audit_fixture` | yes | absent |
| `app-server --stdio -c 'model_reasoning_effort="high"'` | absent/default | **no** | `high` |

Both probes exited 0. Evidence: `upstream/native/version.json`, `config-scope-probe.py`, and `config-scope-result.json`. This directly tests the supported foreground app-server path; it did not send a model request or prove a particular downstream account was used. The consequence is loss of the intended provider/auth/base contract, potentially reverting to native configuration or failing for lack of native login. Do not describe it as demonstrated credential leakage. Existing native tests `TestInstalledCodexManagedAuthEmptyHomeAndCaptureIsolation` and `TestInstalledCodexManagedAuthOverridesInheritedStaticBearer` do not cover a later subcommand `-c`. A correction needs a native scoped-argument regression, preserving intentional user override precedence; waiting for an unreleased upstream fix does not qualify stable 0.163.

**2. Current Cyber CLI syntax is rejected (P2).**

Codex 0.163 declares `--cyber-access-program` as a global value option in `exec`, accepting `standard`, `daybreak_blue`, and `daybreak_red`; upstream also has an exact help-contract test. ViberMate's `codexValueOption` lacks the option, and `walkCodexInvocation` returns `ErrCodexIsolationUnsupported` for it (`internal/runlauncher/codex_isolation.go:124–125,203–215`). [Stable option](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/exec/src/cli.rs#L31-L34), [values](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/exec/src/cli.rs#L88-L102), [upstream help test](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/cli/src/exec_args_tests.rs#L8-L30).

The parent review's `TestAuditStableCodexExecCyberOption` invokes the **actual current** `classifyCodexInvocation` through a Go overlay. Its ordinary `exec --model` control produces no failure; separate and `=value` Cyber forms both return `ErrCodexIsolationUnsupported`. Evidence is in `root-repros/parser-red.log`, `parser-overlay.json`, and `codex_parser_test.go` beneath the review evidence directory. The earlier `upstream/parser-repro/` copied-function harness also rejects `exec resume --last` with the option, but that resume variant is only supplementary evidence. No production parser was replaced or edited. P2 reflects a particular supported native option being blocked, not a failure of all Codex launches. A minimal regression belongs alongside `TestCodexInvocationClass`, covering those forms and rejecting invalid scope without weakening unknown-option handling.

**3. Enterprise requirements are blocked (P1); system-proxy fallback is a separate concern.**

Stable 0.163 skips cloud configuration for accounts that are not eligible. Eligibility explicitly includes Business-like, Education-like, and Enterprise plans using the Codex backend. An eligible account with no valid identity-matched cache fetches the bundle; retry exhaustion returns an error, and configuration loading propagates it. This is not an optional fetch for those accounts. The normal ChatGPT endpoint is `GET https://chatgpt.com/backend-api/wham/config/bundle`. [Eligibility/cache/error path](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/cloud-config/src/service.rs#L52-L60), [startup load](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/cloud-config/src/service.rs#L198-L228), [error after retries](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/cloud-config/src/service.rs#L315-L334), [bundle URL](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/backend-client/src/client.rs#L526-L544).

ViberMate registers `/backend-api/wham/accounts/check` and native models/usage/history, but not `/backend-api/wham/config/bundle` (`internal/operationcatalog/catalog.go:155–166`, `internal/upstreamservice/account_reads.go:63–108`). With a native target scoped to `/backend-api/codex`, `captureassignment.Manager.BeginRequest` rejects paths outside that base unless `AllowsClientRead` explicitly admits them (`internal/captureassignment/manager.go:584–590`). The bundle therefore fails before operation dispatch or credential/transport selection. The existing native test uses a synthetic **Plus** login (`internal/productruntime/codex_account_acceptance_test.go:35–40`) and misses this eligibility boundary.

The parent review supplied three additional controlled results, whose overlay sources and logs were inspected for this revision:

| Test and evidence under `root-repros/` | Observed result |
| --- | --- |
| `TestAuditInstalledCodexEnterpriseAccountBootstrap` — `enterprise-native.log`, `enterprise-overlay.json`, `codex_enterprise_test.go` | Actual native 0.163 `account/read` returns RPC **-32603, `failed to load workspace requirements`** after 6.28 seconds. |
| `TestAuditInstalledCodexPlusAccountBootstrap` — `plus-native.log`, `plus-overlay.json`, `codex_plus_test.go` | Matching Plus control passes in 0.49 seconds. The two test sources differ only in their test name and synthetic plan claim. |
| `TestAuditEnterpriseCloudBundleCatalog` — `bundle-catalog-red.log`, `bundle-catalog-overlay.json`, `codex_bundle_catalog_test.go` | The production proxy returns 200 for `/backend-api/wham/accounts/check`, but **422 `path_unsupported` / `client_target_path_not_allowed`** for `/backend-api/wham/config/bundle`. Its controlled original transport is prepared to return 200 for the bundle; its call count remains **zero**. |

The native cases use the production Runtime/proxy/CA/account fixture, fresh temporary `HOME` and `CODEX_HOME`, synthetic credentials, and an OS sandbox permitting only loopback networking. The boundary test overlays only test code: it adds a deterministic successful fake transport and a counter, then exercises the unchanged production proxy and path-admission logic. That fake response is unreachable and is solely a diagnostic control, not a proposed policy response.

This establishes a **P1 compatibility blocker for the reproduced Enterprise account/bootstrap path with an empty cache**. It does not establish that Plus, API-key, every cached enterprise session, or every possible custom target is broken. Business and Education accounts share the upstream eligibility branch but were not separately run. The observed native failure is `account/read`; a full TUI/model turn was not run. Its error attribution matches upstream's conversion of a failed configuration load into `WorkspaceRoutingError::RequirementsLoad`. [Error mapping](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server/src/request_processors/account_processor/workspace_routing.rs#L215-L240).

Identity matters here: the fixture's native login is workspace A, while managed model/account traffic is configured for B. Codex obtains the cloud policy with its native auth manager and keys its cache by that login's user/account identity; the bundle is a workspace-policy bootstrap operation, not a quota read. The tests prove rejection before forwarding, so they do **not** prove that B's credential or policy was incorrectly used. Any eventual adapter contract must retain the correct workspace policy authority instead of treating the bundle as an interchangeable managed-account read. [Native auth and cache identity](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/cloud-config/src/service.rs#L199-L223), [authenticated bundle request](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/cloud-config/src/backend.rs#L62-L71). Preserve the returned upstream requirements; no blank-policy workaround is recommended.

Separately, #52702 is already in stable 0.163. `system_proxy_fallback` is enabled by default. `exec_bootstrap_get` retries `accounts/check` and `config/bundle` after a five-second whole-request timeout or connect/timeout/request errors, using `RespectSystemProxy`. An OS `Direct` or `Proxy` decision takes precedence over environment proxy settings; only an unavailable OS decision falls back to the environment. Ordinary completed HTTP errors return directly from that helper, and this is not evidence that all model POSTs bypass capture. [Default feature](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/features/src/lib.rs#L1457-L1467), [retry and call sites](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/backend-client/src/client.rs#L343-L407), [route precedence](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/http-client/src/outbound_proxy.rs#L341-L375).

ViberMate supplies upper/lowercase HTTP(S) proxy variables and a protected `NO_PROXY` value (`internal/runlauncher/environment.go:131–138`), but does not constrain either `respect_system_proxy` or `system_proxy_fallback`. The source therefore permits a bootstrap retry outside that environment proxy when the OS selects another route. No OS proxy settings were changed, and no native bypass was executed in this review. A synthetic two-route test should establish the capture behavior before changing launch policy, including explicit managed Codex requirements.

**4. Auth, model-directory, and Daybreak scope.**

Native Codex distinguishes API key, ChatGPT, external ChatGPT tokens, header auth, agent identity, personal access token, and Bedrock modes. Its default model API is ChatGPT's Codex backend for the relevant ChatGPT-associated modes and `api.openai.com/v1` otherwise. Ordinary ViberMate launch leaves native credentials/provider selection intact (`internal/runlauncher/environment.go:190–204`, `internal/runlauncher/invocation.go:32–37`). Its explicit managed-auth mode supplies a separate custom provider and placeholder token; it does not rewrite `auth.json` or turn OAuth into an API key. Upstream resolves that provider's explicit env-key bearer before ambient auth. [Modes](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/login/src/auth/manager.rs#L90-L101), [default endpoint](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/model-provider-info/src/lib.rs#L426-L445), [provider auth ordering](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/model-provider/src/auth.rs#L197-L220).

ViberMate's OAuth importer intentionally accepts `auth_mode="chatgpt"` with the token set, rejecting a nonempty API key (`internal/codexoauth/credential.go:91–130`). That scoped importer is not evidence of broken native API-key launch. Existing synthetic tests cover original login preservation, explicit managed auth, inherited bearer precedence, command-auth conflict rejection, and history resume; their presence is not a fresh 0.163 pass result.

Stable 0.163 already enables API-key model discovery, CLI Daybreak, and API-key Cyber programs. For default OpenAI API-key auth, native model metadata is requested from **ChatGPT's `/backend-api/codex/models?client_version=…`**, while model inference retains the API endpoint. Explicit custom providers/base URLs have different eligibility. [Default features](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/features/src/lib.rs#L1405-L1422), [native catalog routing](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/model-provider/src/models_endpoint.rs#L110-L135), [discovery conditions](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/model-provider/src/models_endpoint.rs#L212-L221).

ViberMate's ChatGPT catalog adapter sends a bounded native `client_version`, defaults to 0.163.0, and permits the native model-directory query (`internal/upstreamendpoint/paths.go:11–16,48–92`, `internal/upstreamservice/model_directory.go`). Its managed per-account preference is applied after final model mapping and exact account leasing; Guardian Red derives Blue, and an incompatible preferred mode can fall back only to Standard explicitly advertised for that exact model (`internal/exchange/cyber_access.go:43–88`, `internal/cyberaccess/programs.go`, related `programs_test.go`). The upstream API-key/ChatGPT Guardian test likewise derives Blue without altering the parent selection. [Guardian contract](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/core/tests/suite/guardian_cyber_access_program_tests.rs#L24-L29).

The gap is specific: `SupportsCyberAccessPrograms` accepts only official ChatGPT origins, and tests explicitly reject `https://api.openai.com` for nonstandard preferences (`internal/provideraccount/types.go:158–163`, `internal/provideraccount/cyber_access_settings_test.go:83–98`). Generic API-account discovery uses `/v1/models`; it does not implement native API-key Codex metadata discovery. Also, native Cyber selection is deliberately restricted to provider ID `openai`, so ViberMate's custom managed provider cannot simply inherit the native picker contract. [Native provider/program filter](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/core/src/cyber_access_program.rs#L19-L62). This is an unsupported capability requiring scoped adapter work, not a reason to broaden all generic Responses endpoints or claim API-key inference is broken.

**5. Transport, sessions, recognition, and CI boundaries.**

The Responses WebSocket fallback contract remains present in stable and main: HTTP 426 during connection switches to HTTP. ViberMate returns that bounded status for the supported Responses upgrade (`internal/loopbackproxy/handler.go:1095–1114`) and disables optional request compression in the Codex recipe. Removing the historical `responses_websockets` feature flag upstream therefore does not alone break the adapter. [Stable fallback](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/core/src/client.rs#L2044-L2049), [HTTP continuation](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/core/src/client.rs#L2387-L2397).

Current Codex exposes `--no-daemon`; ViberMate probes that option for recognized/current interactive clients and injects it, while foreground exec/app-server are already separate processes (`internal/runlauncher/codex_isolation.go:218–242`). It rejects remote/shared-server commands whose network ownership is not established. Native saved-thread selection remains Codex-owned (`internal/runlauncher/codex_session.go:11–14`). The 0.163 release includes cold-resume permission/network restoration (#53150/#53419/#53424); those changes do not replace a new ViberMate capture grant. [Native no-daemon option](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/tui/src/cli.rs#L87-L89), [stable release changes](https://github.com/openai/codex/releases/tag/rust-v0.163.0). The workspace-routing GET is explicitly handled, and upstream skips its background reads without ChatGPT auth. [Upstream guard](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server/src/request_processors/account_processor/workspace_routing.rs#L130-L143).

Exact catalog entries stop at 0.145.0 across the listed platforms plus Darwin arm64 0.159.2/0.160.0. On an exact miss, the verifier tries publisher signatures (`internal/clientadapter/verifier.go:519–535`). Darwin arm64 has native and nested-npm Codex signer recipes (`internal/clientadapter/signer.go:264–301`). Other versions can therefore remain recognized without inheriting release-specific feature claims. A hoisted sibling npm platform package is a separate gap to test: the current wrapper resolves it using Node `require.resolve`, while the signer entry names only the nested package path; the older exact tuples cover sibling layouts. The installed 0.163 binary used here was the nested global npm shape. No claim is made that every install layout/platform fails. [Official wrapper resolution](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-cli/bin/codex.js#L85-L112).

CI's exact Linux package check pins 0.145.0; its current-wire jobs pin 0.159.2, and account-startup tests pin 0.161.0 (`.github/workflows/ci.yml:101–154`). These do not qualify 0.163 or main. Keep the older regression baselines while adding a separately pinned stable matrix, including real release recognition, native configuration scopes, enterprise startup, model-directory auth modes, and HTTP fallback. Preserve Claude and generic-client cases when changing shared launch or routing code.
