# Runtime Module Map

This file is the implementation index for the current production slice. The accepted
design documents and ADRs in the VibeMate design repository remain the
architecture authority. This map records code ownership and current evidence;
it does not redefine product scope.

| Module | Responsibility / non-responsibility | Typed input, output, and authority | Lifecycle | Evidence and current slice |
|---|---|---|---|---|
| `internal/productruntime` | Owns the only production business-component composition sequence, incarnation, internal initialization state, rollback, and shutdown ordering. Provider and original-origin clients remain private implementation dependencies. | Created by `Start`; the Authority shares the Runtime owner context, and only fully constructed components enter bounded LIFO rollback/shutdown. Shutdown first closes proxy, CaptureRun, offline, and Exchange admission; revokes active CaptureRuns; closes transports and hijacked proxy operations; drains Exchanges and egress; then stops the local CA, monitor, approvals, durable managers, Access, and SQLite ownership. ## Initialization and Desktop readiness boundaries

`productruntime.Start` currently proves only that:

1. options and the host descriptor were valid;
2. the SQLite database opened with the required driver and connection policy;
3. all embedded migrations completed and schema state resolved from goose;
4. zero or more committed Access aggregates were validated, compiled, and
   projected from SQLite; an empty Access set is valid;
5. the metadata/write-only credential controller was bound to that sole
   projection and the explicit SecretStore;
6. durable Activity, tool-approval, CaptureRun, and ConnectionEvent authorities
   recovered;
7. the owned storage-health goroutine started;
8. strict remote/literal-loopback provider transport, strict original-origin
   transport, and typed resume probes were constructed;
9. the internal Exchange executor was constructed from the sole Access
   resolver, explicit Messages/Responses protocol-path selector, approval
   authority, Activity observer, and gated provider transport;
10. the persistent local Root, immutable shared operation/PathCapability
   catalogs, and
   authenticated handler-only loopback proxy were constructed;
11. the supplied offline-hold coordinator accepted the runtime incarnation.

The resulting ProductRuntime state is `initialized`, not product-ready.
`desktophost.Start` is the only Desktop readiness commit point:

```text
acquire generation lock
  -> start ProductRuntime
  -> bind literal proxy and control listeners
  -> compose bootstrap, App, CaptureRun, and proxy routes
  -> start both bounded HTTP servers
  -> publish private local control discovery
  -> publish Desktop ready
```

Shutdown withdraws readiness and capabilities first, removes discovery, closes
both listener admissions, drains the control server and ProductRuntime tree,
then drains the proxy server and releases generation ownership. ProductRuntime
still never publishes product discovery itself. No Server readiness endpoint or
Server Host exists.

## Access durable and process-local authority

SQLite is the only persistent Access authority. The in-memory projection is a
read-only optimization for the current process and is not transactionally
atomic with SQLite across media. Each write is serialized through:

```text
validate aggregate ownership and references
  -> compile candidate immutable plan and deterministic hash
  -> SQLite compare-and-swap commit
  -> publish immutable active plan
  -> return success
```

The writer lock covers the CAS-to-publication interval, and projection code
rejects a non-advancing revision. Cancellation before commit rolls back and
does not publish. A known commit is published even if the caller cancels
afterward. An ambiguous commit result is reconciled from SQLite using a bounded
store-owned context; an unrecoverable ambiguity returns
`access_commit_outcome_unknown` rather than implying that no write occurred. An
unreconciled ambiguity or a known commit followed by publication failure marks
that Access ID `access_projection_unavailable`. New resolves and writes for the
affected ID then fail closed; already returned immutable snapshot values do not
change. A new process restores a fresh projection from SQLite.

The recovery test creates durable state without publishing it, performs a
normal bounded store shutdown, reopens the SQLite file, and reconstructs the
projection. Responses recovery recompiles the same operation transport,
revision, content, and hash. These tests prove the close/reopen recovery path,
not recovery from `SIGKILL`, a real process crash, operating-system failure, or
power loss.

This slice proves that an old plan handle remains unchanged, a new resolve
observes the new revision, and exact `ClientOrigin` lookup returns immutable
ingress identity evidence. The proxy integration proves authenticated
CONNECT/MITM, path classification, AgentEndpoint revalidation on every request
of a persistent connection, semantic/opaque dispatch, and body-free connection
auditing. ProductRuntime composition proves that its CaptureRun capability,
ingress projection, local Root, proxy handler, and durable journal are the same
runtime-owned objects. The Exchange suite proves one resolver call, exact
client-operation and ingress-evidence revalidation, explicit
Messages/Responses path selection, gated provider invocation, downstream
commit accounting, no retry after Responses-visible semantics, and redacted
Activity recording. Loopback tests prove an exact Responses HTTP request enters
that typed boundary without client auth or hop-by-hop headers, while a matching
WebSocket upgrade receives a bounded 426 before either data plane. They do not
by themselves prove fixed Codex fallback. A separate clean packaged
fixed-client report proves that rejection selects a second authorized HTTP
connection within the same CaptureRun; it does not prove a successful
WebSocket data plane.

The deterministic repository suite additionally proves Host-owned proxy/control listeners, exact
Webview origin selection, bootstrap capability exchange, local control discovery,
readiness publication/withdrawal, one real `vibermate run` child over loopback,
control Access/credential/approval/offline routes, and rollback if discovery
publication fails. Provider behavior in those tests remains fixture-backed.
Credentialed external reply, real fixed-client streaming/tool approval,
packaged `SIGINT`/force-kill recovery, and SQLite reopen are claimed only for
clean artifacts with passing private acceptance reports. The fixed Codex v4
report is superseded by clean v5 reports for fallback, tool, and Hold detail
claims. Neither the
repository tests nor these reports prove Root trust installation, physical offline/sleep,
unmatched-endpoint blind tunneling, or release secret protection.
Writer serialization is process-local; this slice does not prove that two
simultaneous ProductRuntime processes may safely share one database.
